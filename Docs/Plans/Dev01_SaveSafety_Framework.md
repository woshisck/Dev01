## 2. 原风险与触发链

### 2.1 排队请求没有绑定槽位和数据

旧实现仅使用 `bAsyncSavePending`、`bAsyncSaveQueued` 两个布尔量。写入完成后重新调用 `DoAsyncSave()`，届时再读取当前槽位和当前存档对象。

典型触发顺序：

1. A 槽开始保存状态 A1。
2. A 槽又变化为 A2，再次保存只设置“有待保存”标志。
3. 用户切换到 B 槽，当前槽位和对象被替换。
4. A1 写入完成后，排队动作保存的是 B，而不是 A2。

A2 因而可能没有落盘。旧成功事件同样广播当前对象，可能把 B 当作 A 的保存结果。

### 2.2 删除没有与在途保存协调

旧 `DeleteSlot()` 直接删除文件，未移除该槽的待保存状态，也未等待写入完成。删除与后台写入缺少明确顺序，不能可靠保证删除操作的最终状态。

### 2.3 武器动画层的空值和类型处理错误

主动技能配置 UI 的 `PersistLoadout()` 会调用 `SavePlayer()`。旧实现直接对 `WeaponInst->WeaponLayer` 解引用并调用 `GetClass()`：

- 武器可以没有动画层，空值会进入崩溃路径。
- `WeaponLayer` 本身已经是 `TSubclassOf<UYogAnimInstance>`；继续调用 `GetClass()` 得到的是类对象的元类，不是具体动画类。
- 旧加载代码又将该路径作为 `UBlueprint` 读取，类型不一致；失败时直接跳过武器恢复。

### 2.4 失败和损坏文件缺少明确隔离

旧保存失败主要记录日志，没有保留明确的失败请求供重试。加载失败后的自动创建或后续保存，也缺少阻止覆盖原问题文件的统一槽位保护。

## 3. 实际实施结构

```text
游戏线程中的 UYogSaveGame
  -> 请求当下序列化为字节快照，固定 SlotName
  -> FYogSaveOperationQueue
  -> 单个后台 I/O Future，按顺序处理 Write / Delete
  -> 游戏线程 ticker 收取完成结果
  -> 成功：广播本次已写快照；失败：保留请求并明确报告
```

### 3.1 文件职责

| 文件 | 职责 |
| --- | --- |
| `Source/DevKit/Public/SaveGame/YogSaveOperationQueue.h` | 无 UObject 的操作、结果和队列接口；支持注入执行器；包含可纯逻辑测试的槽位修改 guard / 预览代次状态 |
| `Source/DevKit/Private/SaveGame/YogSaveOperationQueue.cpp` | 顺序执行、待开始写入合并、删除屏障、失败保留与重试 |
| `Source/DevKit/Public/SaveGame/YogSaveSubsystem.h` | 保留原入口，增加 flush、重试、失败事件与写保护查询 |
| `Source/DevKit/Private/SaveGame/YogSaveSubsystem.cpp` | 序列化、存储执行器、槽位操作、生命周期及完成通知 |
| `Source/DevKit/Public/SaveGame/YogWeaponSaveSupport.h` | 动画层保存和兼容加载规则 |
| `Source/DevKit/Private/Tests/SaveGameSafetyTests.cpp` | 无真实磁盘 I/O 的十项自动测试 |

### 3.2 序列化与串行队列

- 每次接受保存请求时，在游戏线程调用 `SaveGameToMemory()`，生成该时刻的字节快照。后台线程不读取实时 UObject。
- 每个请求固定保存 `SlotName`、操作类型和字节快照；后续切槽或修改当前对象不会改变已接受请求。
- 同一时刻只运行一个存储操作。
- 同槽尚未开始的写入可以合并为最新快照，避免高频保存无限累积；已经在途的快照不会被替换。
- 删除是同槽顺序屏障，删除之后的显式新游戏写入不会被合并到删除之前。
- 实际 I/O 使用 UE 存储接口；格式仍由原 `UYogSaveGame` 序列化提供，没有改成另一套自定义文件格式。

### 3.3 槽位切换与预览

- `SelectSlot()` 在读取槽位前 flush 已进入队列的操作，避免读取尚未完成的旧文件状态。
- 写失败时，该槽的最新失败快照保留在内存；同进程再次选择或预览该槽，可以读取这份未落盘状态，避免无声回退到旧磁盘内容。
- `EnsureReservedNormalGameSlot()` 不会用空白默认档覆盖尚未落盘的槽位快照。
- 槽位预览与默认正常槽初始化协调后再读取；仍保留原异步预览接口。
- `SelectSlot()`、`DeleteSlot()` 拒绝越界索引，不把非法操作默默映射到另一个合法槽。
- `SelectSlot()`、`DeleteSlot()`、`ResetSlotForNewGame()` 共用槽位修改 guard。通知回调中的重入切槽/删除/重置只记录日志并返回，不再次广播失败，避免回调递归。
- Reset 使用持锁的私有选择实现，固定请求槽位和选中对象；通知返回后再次核对槽位及对象身份，只有完全匹配才解除写保护并清空该请求对象。
- 每槽维护独立预览代次；接受 Write、Delete 或 Reset 时递增。异步预览捕获槽位、代次与 Subsystem 弱引用，宿主已销毁或代次过期时直接丢弃结果，防止旧预览覆盖删除后的 UI。

切槽、删除、预览等一致性边界可能等待存储操作完成。这里优先保证状态顺序，不承诺这些边界始终无阻塞。

### 3.4 删除

`DeleteSlot()` 的操作顺序为：

1. 移除该槽尚未开始的队列操作和旧失败请求。
2. 将删除请求放到当前在途操作之后。
3. 等待顺序执行完成。
4. 检查文件是否仍存在；失败时不把内存槽位当作已成功删除。
5. 删除成功后再重置对应的当前内存对象；保留原有“正常游戏保留槽”规则。

队列不会让删除前的待写快照在删除后重新写回。删除之后显式开始的新游戏仍可建立新存档，这是正常行为。

### 3.5 成功、失败和重试

原 `OnSaveGameWritten` 事件继续存在，但参数改为从**实际完成请求的字节快照**恢复出的 `UYogSaveGame`，不再使用可能已经属于其他槽的 `CurrentSaveGame`。

新增接口：

| 接口 / 事件 | 语义 |
| --- | --- |
| `FlushPendingSaves()` | 等待已进入队列的操作；存在未恢复的队列失败时返回 `false` |
| `RetryFailedSaves()` | 队列空闲时重新执行保留的失败请求；不进行无限自动重试 |
| `HasSaveFailures()` | 查询队列是否仍保留失败操作；不代替槽位写保护检查 |
| `IsCurrentSlotWriteProtected()` | 查询当前槽是否因读取失败等原因禁止自动写入 |
| `OnSaveOperationFailed(SlotName, Operation, Reason)` | 游戏运行期间向订阅方明确报告失败；同时记录错误日志 |

失败请求只在本次进程内保留。新成功请求可以消除该槽的旧队列失败。关闭进程后无法依靠内存失败队列恢复；没有将失败快照额外写入恢复文件。

新增事件是 UI 接入点，不代表本轮已经制作或接入了保存失败弹窗。上层界面应结合失败事件、flush 返回值和写保护状态决定提示与交互，不应一律显示“保存成功”。

### 3.6 关闭时 flush

- 引擎退出前回调与 Subsystem `Deinitialize()` 共用一次性关闭处理，先停止接收新请求，再调用队列的 `DrainForShutdown()`。
- `DrainForShutdown()` 先 flush 已接受操作；若仍有失败，仅执行一次失败请求重试，然后再次 flush。重试后仍失败时，明确记录最终错误，不循环等待存储恢复。
- 关闭处理及队列 drain 均为幂等操作：先后触发两个退出入口，不会各自再重试一次。
- 等待的是后台 I/O Future，不依赖游戏线程完成回调继续执行，因此不会仅因为回调无法运行而遗留等待中的写入。
- 开始关闭后不再接受新的保存快照。

**flush 只负责已经进入队列的请求，不会自动发现并保存所有尚未提交保存请求的内存变化。** 强制结束进程、系统崩溃和断电不会保证执行这些关闭回调。

这里“有界”指退出重试轮数至多一次，不代表墙钟等待时间有上限。底层存储 I/O 本身若永久阻塞，仍没有超时或取消机制。

### 3.7 损坏 / 不兼容文件保护

- 当已有存档无法加载，或 `SaveFormatVersion` 高于当前程序支持版本时，记录失败并锁住该槽的自动写入，保留原文件。
- 可以建立供当前会话使用的内存对象，但不能据此自动覆盖原问题文件。
- 只有显式新游戏重置或成功删除流程才解除相应槽位的保护。重置是用户授权的破坏性操作，不等同于无损修复。
- 读取失败的设置文件也禁止自动覆盖，使用内存默认值继续运行并报告问题。

这不是完整损坏检测系统：没有新增校验和、文件头完整性验证或全量资产引用有效性验证，也不能保证底层反序列化对任意损坏字节都安全返回。

## 4. 武器保存修复与兼容策略

- `CaptureLayer()` 保存 `WeaponLayer` 本身和实际动画类的 `GetPathName()`；没有动画层时存空值，不进行解引用。
- 加载时接受合法动画 `UClass` 路径，也兼容旧 `UBlueprint` 路径并提取其 `GeneratedClass`。
- 遇到旧版错误元类路径时，尝试已有动画层字段或武器类默认值，不再仅因层路径错误就跳过整个武器。
- 先生成武器但暂不链接动画层，再应用旧实例保存字节，最后链接实际恢复出来的非空动画层。旧字节可能仍含正确的实例层属性。
- 保存玩家前先验证角色、属性与 ASC 依赖；保存前清空旧 OwnedTags 快照，避免已消失的状态残留；空的对象保存字节不再强行反序列化。

兼容恢复依赖仍存在且类型正确的武器/动画类。已经删除、改名但没有重定向的资源，或自身损坏的实例保存字节，不保证能够自动恢复。

## 6. 明确未实现的边界与后续方向

本轮没有实现：

- 临时文件写入、刷盘和原子替换协议。
- 原存档的上一版备份、轮换备份或故障自动回滚。
- 将失败队列持久化为恢复日志。
- 校验和、完整性校验及全量反序列化沙箱。
- 跨进程锁；两个独立游戏/编辑器进程仍不能同时安全管理同一组槽位。
- 对操作系统 I/O 永久卡住的取消或超时机制。
- 对所有历史保存入口、调用时机与内存状态采集的统一重构。
- 本轮审查提到的游玩时长统计修复。

当前底层仍通过 UE 保存接口写文件。若写入被断电、强杀、磁盘满或设备故障打断，文件仍可能不完整；错误事件不能把已经损坏的旧文件自动变回原状。

若后续要求断电恢复能力，应作为独立阶段设计并验证“写临时文件 → 验证内容 → 保留上一版 → 原子替换 → 启动时恢复”的协议，结合目标 Windows 文件系统和真实故障注入测试。不能只增加一处 `try/catch` 或保存前复制动作，就宣称绝对可靠。
